# Loom TUI 交互架构

## 概述

本文档描述 Loom TUI 的交互架构（Interaction Architecture）——定义用户与系统之间交互的完整框架。包括事件处理模型、视图管理机制、状态机设计、以及交互组件之间的协作关系。

交互架构独立于具体的渲染实现，聚焦于"用户的操作如何被理解、路由、响应"。

---

## 1. 交互架构总览

### 1.1 架构层级

```
┌─────────────────────────────────────────────────────────────────┐
│  用户输入 (键盘 / 粘贴 / resize / 焦点)                          │
└──────────────────────────┬──────────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────────────┐
│  1. 事件捕获层 (Event Capture)                                   │
│  将原始终端事件转换为 TuiEvent 枚举                              │
│  crossterm → TuiEventStream → EventBroker                       │
└──────────────────────────┬──────────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────────────┐
│  2. 事件路由层 (Event Routing)                                   │
│  将事件分发到正确的处理目标                                      │
│  ├── 全局事件 (Ctrl+C, Ctrl+Z, Ctrl+D) →  App 级处理            │
│  ├── 视图事件 (方向键, Enter)    →  PaneStack 路由              │
│  └── 系统事件 (Resize, Draw)     →  Tui 级处理                  │
└──────────────────────────┬──────────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────────────┐
│  3. 视图管理层 (View Management)                                 │
│  管理视图栈的 push/pop 和事件委托                                │
│  PaneStack: Vec<Box<dyn PaneView>>                              │
│  ├── 栈顶视图优先处理事件                                        │
│  ├── 未处理事件向下传递                                          │
│  └── 视图完成时自动 pop                                         │
└──────────────────────────┬──────────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────────────┐
│  4. 业务逻辑层 (Business Logic)                                  │
│  处理具体的交互语义                                              │
│  ├── ChatComposer: 文本编辑、历史、命令                          │
│  ├── ApprovalOverlay: 审批逻辑                                  │
│  ├── ListSelectionView: 选择逻辑                                │
│  └── 状态管理: 7 种状态的状态机                                  │
└──────────────────────────┬──────────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────────────┐
│  5. 系统响应层 (System Response)                                 │
│  触发后端操作、更新 UI 状态                                     │
│  ├── 提交输入 → Agent 运行                                      │
│  ├── 审批响应 → 发送到 Agent 后端                               │
│  └── 状态更新 → 渲染触发                                        │
└─────────────────────────────────────────────────────────────────┘
```

### 1.3 交互架构的关键能力

| 能力 | 说明 | 实现机制 |
|------|------|----------|
| **事件路由** | 将原始事件分发到正确的处理目标 | EventBroker + PaneStack 委托 |
| **视图栈管理** | 管理多个视图的叠加和切换 | Vec<Box<dyn PaneView>> push/pop |
| **状态机** | 管理交互状态的转换 | 有限状态机 (FSM) |
| **按键映射** | 可配置的按键到行为的映射 | Keymap 注册表 |
| **通知** | 异步事件提醒 | 桌面通知系统 |
| **中断处理** | 用户中断当前操作 | Ctrl+C → 中断确认流程 |

## 2. 事件处理模型

### 2.1 事件流架构

```
┌─────────────────────────────────────────────────────────────────┐
│                    事件处理管道                                   │
├─────────────────────────────────────────────────────────────────┤
│                                                                   │
│  原始事件源                                                       │
│  crossterm::EventStream                                          │
│       │                                                           │
│       ▼                                                           │
│  TuiEventStream (包装层)                                          │
│  ├── KeyEvent → TuiEvent::Key                                    │
│  ├── Paste(文本) → TuiEvent::Paste                               │
│  ├── Resize → TuiEvent::Resize                                   │
│  ├── FocusGained/Lost → 更新 terminal_focused                    │
│  └── 定时器 → TuiEvent::Draw                                     │
│       │                                                           │
│       ▼                                                           │
│  EventBroker (分发层)                                             │
│  ├── Arc 共享，支持 pause/resume                                 │
│  ├── 多消费者支持                                                │
│  └── 线程安全                                                    │
│       │                                                           │
│       ▼                                                           │
│  App 主循环 (tokio::select!)                                      │
│  ├── TuiEvent::Key → handle_key()                                │
│  ├── TuiEvent::Paste → handle_paste()                            │
│  ├── TuiEvent::Resize → handle_resize()                          │
│  ├── TuiEvent::Draw → render()                                   │
│  └── TuiEvent::Resume → handle_resume()                          │
│                                                                   │
└─────────────────────────────────────────────────────────────────┘
```

### 2.2 事件优先级

事件按优先级处理，高优先级事件优先响应：

| 优先级 | 事件类型 | 处理目标 | 说明 |
|--------|----------|----------|------|
| **最高** | `Ctrl+Z` | `SuspendContext` | 暂停优先于一切 |
| **高** | `Ctrl+C` | 当前 PaneView.on_ctrl_c() | 中断优先于内容处理 |
| **高** | `Resize` | Tui 视图管理 | 布局调整优先于交互 |
| **中** | 键盘事件 | PaneStack 路由 | 正常交互事件 |
| **中** | `Paste` | ChatComposer | 粘贴内容 |
| **低** | `Draw` | 渲染管线 | 帧同步 |

### 2.3 事件处理契约

每个事件处理函数遵循以下契约：

```rust
/// 处理结果
pub enum Handled {
    /// 事件已处理，无需继续传递
    Handled,
    /// 事件未处理，传递给下一层
    NotHandled,
}

/// Ctrl+C 处理结果
pub enum CtrlCAction {
    /// 未处理，默认行为
    NotHandled,
    /// 已处理，无需中断
    Handled,
    /// 确认中断
    Cancel,
}
```

## 3. 视图栈 (PaneStack) 架构

### 3.1 核心设计

PaneStack 是交互架构的核心，采用**栈式视图管理**：

```
PaneStack
  └── Vec<Box<dyn PaneView>>
      ├── [基座] ChatComposer     ← 始终存在，不可移除
      ├── [push] ApprovalOverlay   ← 审批弹窗，完成后自动 pop
      ├── [push] ListSelectionView ← 选择列表，完成后自动 pop
      └── ...
```

### 3.2 PaneView 接口

所有视图组件必须实现 PaneView trait：

```rust
pub trait PaneView: Renderable {
    /// 处理按键事件
    /// 返回 Handled 表示已处理，NotHandled 表示传递给下一层
    fn handle_key_event(&mut self, key: KeyEvent) -> Handled;

    /// 视图是否已完成
    /// 返回 true 时，PaneStack 自动 pop 此视图
    fn is_complete(&self) -> bool;

    /// Ctrl+C 处理
    /// 视图可以返回 Cancel 来触发中断流程
    fn on_ctrl_c(&mut self) -> CtrlCAction;

    /// 视图标识符
    fn view_id(&self) -> Option<&'static str>;
}
```

### 3.3 事件路由规则

```
用户按键
  │
  ▼
PaneStack::handle_key_event(key)
  │
  ├── 栈顶视图存在?
  │   ├── 是 → 调用栈顶视图的 handle_key_event()
  │   │         ├── Handled → 事件处理完成
  │   │         └── NotHandled → 传递给下一层
  │   │
  │   └── 否 → 事件未处理，丢弃
  │
  └── 检查栈顶视图是否完成?
      ├── is_complete() == true → pop 视图
      └── is_complete() == false → 保持当前状态
```

### 3.4 视图生命周期

```
视图生命周期:
  ┌──────────┐
  │  Created  │ ← push 到 PaneStack
  └────┬─────┘
       │
       ▼
  ┌──────────┐
  │  Active   │ ← 栈顶，接收事件
  └────┬─────┘
       │
       ├── is_complete() == true → pop
       │
       └── 用户按 Esc → 取消 → pop
              │
              ▼
  ┌──────────┐
  │  Destroyed│ ← 从 PaneStack 移除
  └──────────┘
```

### 3.5 视图类型

| 视图 | 视图 ID | 基座 | 生命周期 | 完成条件 |
|------|---------|------|----------|----------|
| `ChatComposer` | `"composer"` | ✅ 是 | 始终存在 | 永不完成 |
| `ApprovalOverlay` | `"approval"` | ❌ | push → 响应 → pop | 用户响应后 |
| `ListSelectionView` | `"selection"` | ❌ | push → 选择 → pop | 选择或取消 |
| `FeedbackView` | `"feedback"` | ❌ | push → 提交 → pop | 提交或取消 |
| `CustomPromptView` | `"custom-prompt"` | ❌ | push → 提交 → pop | 提交或取消 |

## 4. 状态机设计

### 4.1 应用状态机 (App State Machine)

管理应用的整体交互状态：

```
                    ┌───────────┐
                    │   Idle    │ ← 等待用户输入
                    └─────┬─────┘
                          │ 用户提交输入
                          ▼
                    ┌──────────────┐
                    │  Submitting  │ ← 提交处理中
                    └──────┬───────┘
                           │ 提交完成
                           ▼
                    ┌─────────────┐
              ┌─────│  Waiting    │ ← 等待 AI 响应
              │     └──────┬──────┘
              │            │ AI 开始输出
              │            ▼
              │     ┌──────────────┐
              │     │  Streaming   │ ← AI 流式输出中
              │     └──────┬───────┘
              │            │ AI 请求审批 / AI 完成
              │            ▼
              │     ┌──────────────────┐
              │     │  WaitingApproval │ ← 等待用户审批
              │     └────────┬─────────┘
              │              │ 用户响应
              │              ▼
              │     ┌──────────────┐
              │     │  Executing   │ ← AI 执行操作
              │     └──────┬───────┘
              │            │ 执行完成
              │            ▼
              │     ┌───────────┐
              └─────│   Idle    │ ← 回到空闲
                    └───────────┘

其他状态转换:
  Any State ──→ Interrupted (Ctrl+C)
  Any State ──→ Suspended (^Z)
  Any State ──→ Error (异常)
```

### 4.2 输入状态机 (Input State Machine)

管理 ChatComposer 的输入状态：

```
                    ┌───────────┐
                    │   Empty   │ ← 输入框为空
                    └─────┬─────┘
                          │ 用户输入字符
                          ▼
                    ┌───────────┐
              ┌─────│  Editing  │ ← 正在编辑
              │     └─────┬─────┘
              │           │ 用户输入 /
              │           ▼
              │     ┌──────────────┐
              │     │ PopupActive  │ ← 弹出菜单活跃
              │     └──────┬───────┘
              │            │ 选择/取消
              │            ▼
              │     ┌───────────┐
              └─────│  Editing  │
                    └─────┬─────┘
                          │ 用户按 Enter (提交)
                          ▼
                    ┌──────────────┐
                    │  Submitting  │ ← 提交中
                    └──────┬───────┘
                           │ 提交完成
                           ▼
                    ┌───────────┐
                    │   Empty   │ ← 清空输入框
                    └───────────┘
```

### 4.3 状态转换事件表

| 当前状态 | 事件 | 下一状态 | 副作用 |
|----------|------|----------|--------|
| Idle | 用户提交 | Submitting | 禁用输入框，启动 spinner |
| Submitting | 提交完成 | Waiting | 发送请求到 Agent |
| Waiting | AI 开始输出 | Streaming | 显示流式输出 |
| Streaming | AI 请求审批 | WaitingApproval | push ApprovalOverlay |
| Streaming | AI 完成 | Idle | 回到空闲，通知 |
| WaitingApproval | 用户同意 | Executing | 通知 AI 继续 |
| WaitingApproval | 用户拒绝 | Idle | 通知 AI 取消 |
| Executing | 执行完成 | Idle | 回到空闲 |
| * | Ctrl+C | Interrupted | 中断当前操作 |
| * | ^Z | Suspended | 暂停事件流 |
| * | 异常 | Error | 显示错误信息 |

## 5. 按键映射系统 (Keymap)

### 5.1 架构设计

按键映射系统采用**运行时动态绑定**，支持不同视图有不同的按键映射：

```
                         ┌──────────────┐
                         │  KeymapRegistry │
                         │  (全局注册表)   │
                         └──────┬───────┘
                                │
         ┌──────────────────────┼──────────────────────┐
         │                      │                      │
         ▼                      ▼                      ▼
┌──────────────────┐  ┌──────────────────┐  ┌──────────────────┐
│ Global Keymap    │  │ View Keymap      │  │ Context Keymap   │
│ (全局快捷键)      │  │ (视图特定映射)    │  │ (上下文映射)      │
│                  │  │                  │  │                  │
│ Ctrl+C → 中断    │  │ Enter → 提交     │  │ / → 命令模式     │
│ Ctrl+Z → 暂停    │  │ ↑/↓ → 历史      │  │ Y → 同意         │
│ Ctrl+D → 退出    │  │ Esc → 取消      │  │ N → 拒绝         │
└──────────────────┘  └──────────────────┘  └──────────────────┘
```

### 5.2 按键映射优先级

```
1. 全局按键 (Global Keymap)
   - 始终生效，优先级最高
   - Ctrl+C, Ctrl+Z, Ctrl+D, Tab

2. 视图特定按键 (View Keymap)
   - 仅当前活跃视图生效
   - 由 PaneView::handle_key_event() 处理

3. 上下文按键 (Context Keymap)
   - 特定状态下生效
   - 如审批模式下的 Y/N/D/A
```

### 5.3 按键冲突处理

```
当按键被多个映射匹配时:
  1. 全局映射优先
  2. 视图映射次之
  3. 上下文映射最后

示例: Ctrl+C
  - 全局: 中断当前操作
  - 视图: 如果视图实现了 on_ctrl_c()，优先调用
  - 如果视图返回 NotHandled，执行全局中断行为
```

## 6. 通知系统架构

### 6.1 通知流程

```
系统事件
  │
  ▼
┌─────────────────────────────────────────────────────────────┐
│                    通知调度器                                 │
│                                                             │
│  1. 判断通知条件:                                            │
│     - 终端是否失焦?                                          │
│     - 用户通知偏好? (Unfocused / Always / Never)            │
│                                                             │
│  2. 选择通知后端:                                            │
│     - macOS: 系统通知中心                                    │
│     - Linux: notify-send / dbus                             │
│     - Windows: toast notification                            │
│                                                             │
│  3. 发送通知:                                                │
│     - 标题: Loom TUI                                        │
│     - 正文: 事件描述                                         │
│     - 失败时自动禁用                                         │
└─────────────────────────────────────────────────────────────┘
```

### 6.2 通知类型

| 通知类型 | 触发条件 | 通知内容 | 是否可配置 |
|----------|----------|----------|-----------|
| `ReplyComplete` | AI 回复完成 | "AI 已完成回复" | ✅ 可关闭 |
| `ApprovalRequired` | AI 请求审批 | "AI 请求修改文件: xxx" | ✅ 必须 |
| `Error` | 系统错误 | "发生错误: xxx" | ✅ 可关闭 |
| `SubTaskComplete` | 子代理完成 | "子任务已完成" | ❌ 默认关闭 |

### 6.3 通知抑制策略

```
通知条件判断:
  if terminal_focused && notification_condition == Unfocused:
    → 不通知 (用户正在终端前)
  if notification_condition == Never:
    → 不通知 (用户已关闭)
  if notification_condition == Always:
    → 始终通知

通知频率控制:
  同一类型通知 5 秒内不重复发送
```

## 7. 中断处理架构

### 7.1 中断流程

```
用户按 Ctrl+C
  │
  ▼
App::handle_key(Ctrl+C)
  │
  ├── 当前有活跃视图?
  │   ├── 是 → 调用视图的 on_ctrl_c()
  │   │         ├── CtrlCAction::Cancel → 执行中断
  │   │         ├── CtrlCAction::Handled → 视图已处理
  │   │         └── CtrlCAction::NotHandled → 执行默认中断
  │   │
  │   └── 否 → 执行默认中断
  │
  ▼
中断流程:
  1. 停止当前 AI 操作
  2. 清理未完成的流式输出
  3. 将状态切换为 Interrupted
  4. 显示中断提示
  5. 回到 Idle
```

### 7.2 中断级别

| 级别 | 说明 | 处理方式 |
|------|------|----------|
| **Soft** | 中断当前操作 | 等待 AI 完成当前 token 后停止 |
| **Hard** | 立即中断 | 立即断开与 AI 的连接 |
| **Cancel** | 取消当前视图 | 仅 pop 视图，不中断 AI |

## 9. 状态一致性

### 9.1 状态来源

交互架构采用**单一状态来源（Single Source of Truth）**原则：

```
App 结构体持有完整状态:
  App {
    app_state: AppState,          // 应用状态机状态
    pane_stack: PaneStack,        // 视图栈状态
    chat_composer: ChatComposer,  // 输入状态
    history: Vec<HistoryCell>,    // 对话历史
    // ...
  }
```

### 9.2 状态同步

```
状态更新流程:
  1. 事件处理 → 更新 App 内部状态
  2. 状态更新 → 触发 render()
  3. render() → 从 App 状态生成 UI
  4. UI 反映最新状态

保证:
  - 所有状态变更通过 App 方法
  - 渲染始终从最新状态生成
  - 无并发状态修改
```

### 9.3 并发安全

```
跨线程状态:
  - terminal_focused: Arc<AtomicBool>
  - 其他: 仅在 App 主循环中访问

事件通道:
  - Agent 事件: mpsc channel (保证顺序)
  - TUI 事件: EventBroker (单消费者)
```

## 11. 架构决策记录

### ADR-1: 栈式视图而非多窗口

**决策**：采用 PaneStack 栈式视图管理，而非多窗口系统。
**理由**：终端屏幕空间有限，栈式管理更自然（先进后出），实现简单。
**后果**：不支持多视图同时可见，但适用于对话式交互场景。

### ADR-2: 事件委托而非广播

**决策**：事件从栈顶视图向下委托，而非广播到所有视图。
**理由**：栈顶视图最优先，避免事件冲突。未处理事件自然向下传递。
**后果**：视图间无法监听彼此事件，但交互逻辑更清晰。

### ADR-3: 单一状态来源

**决策**：App 持有完整状态，所有状态变更通过 App 方法。
**理由**：状态一致性好，无需跨组件同步。渲染从最新状态生成。
**后果**：App 结构体较大，但可维护性高。

### ADR-4: 运行时按键映射

**决策**：按键映射通过运行时注册表动态绑定，而非硬编码。
**理由**：支持不同视图有不同的按键映射，可配置性强。
**后果**：需要维护 KeymapRegistry，但灵活性高。

## 12. 总结

Loom TUI 的交互架构以**事件驱动**为核心，通过**栈式视图管理**组织交互组件，**状态机**确保行为可预测，**按键映射系统**提供灵活性。

核心设计原则：
1. **事件从顶向下**：栈顶视图优先处理，未处理事件自然传递
2. **视图即服务**：每个视图封装独立的交互逻辑，通过 PaneView trait 统一
3. **状态即契约**：状态机定义所有可能的状态转换，行为可预测
4. **用户始终可控**：中断机制、审批流程、通知系统确保用户掌控权
