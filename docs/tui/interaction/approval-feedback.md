# Loom TUI 交互文档 - 审批与反馈视图

## 概述

审批与反馈视图是 Loom TUI 中确保用户安全和控制的关键交互组件。当 AI 需要执行敏感操作（如文件修改、命令执行）或需要用户决策时，系统会弹出相应的审批界面，让用户明确授权或拒绝。反馈视图则用于收集用户对系统表现的评价和建议，形成完整的用户-系统协作闭环。

## 1. 审批流程架构

### 1.1 完整端到端流程

```
┌─────────────────────────────────────────────────────────────────┐
│                    审批流程端到端设计                             │
└─────────────────────────────────────────────────────────────────┘

AI 发起审批请求
  │
  ├── Agent 后端生成审批请求
  │   ├── 创建审批 ID (call_id / item_id)
  │   ├── 生成审批上下文 (文件路径、命令、风险等级)
  │   └── 发送审批通知到 TUI 层
  │
  ▼
TUI 事件处理层
  │
  ├── 接收审批通知 (Notification::ApprovalRequest)
  │   ├── 解析审批参数
  │   └── 创建 ApprovalOverlay 实例
  │
  ▼
PaneStack 视图管理
  │
  ├── push ApprovalOverlay 到视图栈
  │   ├── 停止 ChatComposer 输入
  │   ├── 显示审批界面
  │   └── 切换状态到 WaitingApproval
  │
  ▼
用户交互处理
  │
  ├── 用户按 Y / Enter (接受)
  │   ├── 发送 approve 响应到 Agent
  │   ├── 调用 ApprovalManager::resolve(call_id, true)
  │   └── pop 返回 ChatComposer
  │
  ├── 用户按 N (拒绝)
  │   ├── 发送 deny 响应到 Agent
  │   ├── 调用 ApprovalManager::resolve(call_id, false)
  │   └── pop 返回 ChatComposer
  │
  ├── 用户按 D (查看差异)
  │   ├── push DiffView 视图
  │   ├── 显示文件差异详情
  │   └── 用户可在 DiffView 中选择接受/拒绝
  │
  ├── 用户按 A (始终允许)
  │   ├── 记录用户偏好到会话状态
  │   ├── 发送 approve 响应到 Agent
  │   ├── 设置全局审批策略为 always
  │   └── pop 返回 ChatComposer
  │
  └── 用户按 Esc (取消)
      ├── 发送 deny 响应到 Agent
      └── pop 返回 ChatComposer
```

### 1.2 审批请求协议

基于 Codex 的 JSON-RPC 审批协议，Loom TUI 采用类似的通信机制：

```json
// Agent 发送审批请求
{
  "jsonrpc": "2.0",
  "method": "thread/commandExecution/requestApproval",
  "params": {
    "commandExecutionId": "call-123",
    "command": "rm -rf /tmp/test",
    "riskLevel": "high"
  }
}

// 客户端响应同意
{
  "jsonrpc": "2.0",
  "method": "thread/commandExecution/approve",
  "params": {
    "commandExecutionId": "call-123"
  },
  "id": "client-request-1"
}

// 客户端响应拒绝
{
  "jsonrpc": "2.0",
  "method": "thread/commandExecution/deny",
  "params": {
    "commandExecutionId": "call-123"
  },
  "id": "client-request-2"
}
```

### 1.3 ApprovalManager 机制

参考 Codex 的 ApprovalManager 实现，Loom TUI 使用类似的待处理审批管理机制：

```rust
pub struct ApprovalManager {
    pending: Mutex<HashMap<String, oneshot::Sender<bool>>>,
    output_tx: mpsc::Sender<OutputEvent>,
}

impl ApprovalManager {
    /// 发送审批请求并等待用户响应
    pub async fn request(&self, call_id: String, command: String) -> ApprovalResult {
        let (tx, rx) = oneshot::channel();
        {
            let mut pending = self.pending.lock().unwrap();
            pending.insert(call_id.clone(), tx);
        }

        // 发送审批通知到客户端
        let notif = ApprovalNotification {
            method: "thread/commandExecution/requestApproval".to_string(),
            params: json!({
                "commandExecutionId": call_id,
                "command": command,
            }),
        };
        let _ = self.output_tx.send(OutputEvent::Notification(notif)).await;

        // 等待用户响应，通道错误视为拒绝
        match rx.await {
            Ok(true) => ApprovalResult::Approved,
            _ => ApprovalResult::Denied,
        }
    }

    /// 解析审批结果
    pub fn resolve(&self, call_id: &str, approved: bool) {
        let mut pending = self.pending.lock().unwrap();
        if let Some(tx) = pending.remove(call_id) {
            let _ = tx.send(approved);
        }
        // 如果 call_id 未找到，静默忽略过期或已解析的请求
    }
}
```

### 2.2 按键映射

| 按键 | 功能 | 说明 |

### 2.3 多文件支持

当 AI 请求修改多个文件时，ApprovalOverlay 提供文件浏览和选择功能：

```
文件选择交互:
  1. 初始状态: 默认选择第一个文件，显示其差异预览
  2. 用户按 ↑/↓: 在文件列表中移动，实时更新差异预览
  3. 用户按 Y: 接受所有文件的修改
  4. 用户按 N: 拒绝所有文件的修改
  5. 用户按 D: 为当前选择的文件推送 DiffView
```

### 2.4 审批策略

从 Codex 的 `approval_policy` 参数推导，Loom TUI 支持多种审批策略：

| 策略 | 触发条件 | 行为 | 配置方式 |
|------|----------|------|----------|
| `on-request` | 默认策略 | 每次操作都询问用户 | 启动参数或配置文件 |
| `on-view` | 修改复杂时 | 用户查看差异后询问 | 根据修改行数和风险等级自动选择 |
| `always` | 用户信任时 | 始终允许操作 | 用户按 A 设置会话级策略 |
| `never` | 用户严格时 | 始终拒绝操作 | 配置文件设置 |

### 2.5 风险等级评估

系统自动评估操作的风险等级，影响审批策略和界面提示：

```
风险等级判断:
  - 🟢 低风险: 只读操作、文件创建、配置修改
  - 🟡 中风险: 文件修改、包安装、依赖更新
  - 🔴 高风险: 删除操作、系统命令、网络连接
  - 🟣 危险: 破坏性命令、敏感数据访问

风险等级影响:
  - 中高风险显示风险提示
  - 高风险强制用户查看差异
  - 危险操作显示警告界面，要求二次确认
```

### 3.3 命令执行状态追踪

参考 Codex 的 ItemTracker 实现，Loom TUI 完整追踪命令执行的生命周期：

```rust
// 命令执行状态转换
pending → running → completed/failed

// 状态机
enum CommandExecutionState {
    Pending,       // 等待用户审批
    Running,       // 正在执行
    Completed,     // 成功完成
    Failed,        // 执行失败
    UserDenied,    // 用户拒绝
    Timeout,       // 超时
}

// ItemTracker 状态追踪
pub struct ItemTracker {
    tool_item_ids: HashMap<String, String>,     // call_id → item_id 映射
    tool_output: HashMap<String, String>,       // 累积的输出
    tool_command: HashMap<String, String>,      // 命令字符串
}
```

## 6. 对抗性验证

### 6.1 边缘情况处理

#### 审批超时
```
场景: 用户长时间不响应审批请求
处理策略:
  1. 设置默认超时时间 (30 秒)
  2. 超时后自动拒绝审批
  3. 通知 AI 操作被拒绝 (timeout)
  4. 记录超时事件到日志

风险: 用户临时离开但希望批准
缓解: 提供延长超时选项，或支持审批队列
```

#### 重复审批
```
场景: 同一个操作被多次请求审批
处理策略:
  1. 基于 call_id 去重
  2. ApprovalManager pending map 中检查重复
  3. 重复请求自动使用之前的结果

实现参考:
  // 从 Codex ApprovalManager::resolve 推导
  pub fn resolve(&self, call_id: &str, approved: bool) {
      let mut pending = self.pending.lock().unwrap();
      if let Some(tx) = pending.remove(call_id) {
          let _ = tx.send(approved);
      }
      // 如果 call_id 未找到，静默忽略过期或已解析的请求
  }
```

#### 审批与取消竞争
```
场景: 用户在审批过程中同时按 Ctrl+C
处理策略:
  1. Ctrl+C 优先级高于审批操作
  2. 中断当前审批流程
  3. 清理 pending 状态
  4. 通知 AI 操作被中断

优先级规则:
  Ctrl+C > 审批响应 > 其他操作
```

### 6.2 失败模式分析

#### ApprovalManager pending 泄露
```
风险: pending map 中的审批请求未能正确清理
原因:
  1. 网络异常导致通知未发送
  2. 用户直接关闭终端
  3. 崩溃或异常退出

防护措施:
  1. 定期清理超时的 pending 请求
  2. 进程退出时清理所有 pending
  3. 监控 pending map 大小
  4. 设置 pending 数量上限

清理机制:
  // 定期清理超时请求
  fn cleanup_expired(&self) {
      let mut pending = self.pending.lock().unwrap();
      let now = Instant::now();
      pending.retain(|_, _| now.duration_since(start_time) < TIMEOUT);
  }
```

#### 视图未正确 pop
```
风险: ApprovalOverlay 完成后未从 PaneStack 移除
原因:
  1. is_complete() 逻辑错误
  2. 异常导致跳过 pop 操作
  3. 用户快速连续操作导致状态不一致

防护措施:
  1. 强制完成条件: 用户响应后立即完成
  2. 异常时自动清理视图栈
  3. 定期检查视图栈状态
  4. 限制视图栈深度

安全检查:
  // 确保视图正确 pop
  if approval_overlay.is_complete() {
      pane_stack.pop();
      assert!(!pane_stack.contains_approval());
  }
```

### 6.3 安全考量

#### 命令注入防护
```
风险: 恶意代码通过命令执行攻击系统
防护措施:
  1. 命令解析和验证
     - 检测危险命令组合
     - 阻止 shell 元字符注入
     - 限制可执行命令类型

  2. 沙箱执行
     - 使用受限的执行环境
     - 限制文件系统访问
     - 网络访问控制

  3. 用户感知
     - 显示完整命令字符串
     - 风险等级明确标识
     - 高风险操作强制二次确认

危险命令检测:
  const DANGEROUS_PATTERNS: &[&str] = &[
      "rm -rf /",
      "format c:",
      ":(){ :|:& };:",
      "wget.*|sh",
      "curl.*|bash",
  ];
```

#### 审批绕过防护
```
风险: AI 试图绕过审批机制直接执行操作
防护措施:
  1. 强制审批路径
     - 所有敏感操作必须经过 ApprovalManager
     - 禁止绕过审批的直接执行
     - 审批状态检查点

  2. 审计日志
     - 记录所有审批请求和响应
     - 追踪操作完整链路
     - 异常审批模式检测

  3. 策略强制
     - 配置文件中的审批策略不可被 AI 修改
     - 始终允许策略需要用户明确确认
     - 策略变更需要重新验证

强制检查:
  // 所有敏感操作必须经过审批
  if is_sensitive_operation(&operation) && !has_approval(&operation) {
      return Err(OperationDenied::NoApproval);
  }
```

#### 始终允许的安全风险
```
风险: 用户设置"始终允许"后失去对 AI 的控制
防护措施:
  1. 临时性策略
     - "始终允许"仅对当前会话有效
     - 会话结束自动重置
     - 支持随时撤销策略

  2. 策略范围限制
     - 细粒度策略控制 (按命令类型、文件类型)
     - 不支持全局"始终允许"策略
     - 高风险操作仍需单独审批

  3. 用户提醒
     - 设置策略时显示风险提示
     - 长时间使用建议重新评估策略
     - 提供策略查看和修改界面

策略管理:
  pub struct ApprovalPolicy {
      pub session_only: bool,        // 仅当前会话
      pub command_patterns: Vec<String>, // 适用的命令模式
      pub expires_at: Option<DateTime>, // 过期时间
  }
```

### 6.4 设计权衡

#### 同步审批 vs 异步审批
```
同步审批:
  优点: 逻辑简单，状态一致性容易保证
  缺点: 阻塞 AI 执行，用户体验较差

异步审批:
  优点: AI 可继续其他任务，用户体验更好
  缺点: 状态复杂，需要处理并发和竞态

Loom TUI 选择: 混合方案
  - 文件修改: 同步审批 (必须立即决策)
  - 命令执行: 异步审批 (可排队处理)
  - 低风险操作: 可配置异步或同步
```

#### 审批队列 vs 单一审批
```
单一审批:
  优点: 逻辑简单，用户专注当前操作
  缺点: AI 并行执行时用户体验差

审批队列:
  优点: 支持批量审批，用户效率高
  缺点: 界面复杂，状态管理困难

Loom TUI 选择: 动态队列
  - 少量操作 (< 3): 单一审批视图
  - 中等操作 (3-10): 批量审批列表
  - 大量操作 (> 10): 审批队列 + 分页
```

#### 超时策略
```
严格超时:
  超时时间: 30 秒
  行为: 自动拒绝
  适用: 高风险操作

宽松超时:
  超时时间: 5 分钟
  行为: 提醒用户，延长超时
  适用: 低风险操作

无超时:
  超时时间: 无限制
  行为: 等待用户响应
  适用: 配置操作

Loom TUI 选择: 分级超时
  - 高风险: 严格超时
  - 中风险: 宽松超时
  - 低风险: 无超时
  - 用户可自定义超时策略
```
