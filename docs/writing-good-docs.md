# 好文档的标准

## 1. 准确性

- 代码示例必须可直接运行，版本号、参数名、返回值与实际一致
- 有变更时同步更新文档，理想状态下文档与代码在同一 PR 中修改
- 标注适用的版本范围，避免读者在错误版本上尝试

## 2. 清晰性

- 一个段落只讲一件事，一个句子只有一个核心意思
- 用主动语态、动词开头（"调用此函数返回…" 而非 "此函数被调用后会…"）
- 避免未定义的术语；首次出现时给出解释
- 中英文混排时保持一致的排版规范（如中英文之间加空格）

## 3. 可发现性

- 有清晰的目录结构和导航层级
- 文件/页面命名直观，URL 可读（`/docs/api/auth` 而非 `/docs/page12`）
- 提供全文搜索能力
- 交叉引用：相关概念之间有明确的链接跳转
- 入口文档指明"从哪里开始阅读"的推荐路径

## 4. 完整性 — 分层覆盖不同读者

| 文档类型 | 目标读者 | 内容 |
|---|---|---|
| Quick Start / Getting Started | 新用户 | 5-10 分钟跑通 hello world |
| 概念指南 | 架构师 / 决策者 | 设计理念、核心抽象、适用场景 |
| 教程 / How-to | 开发者 | 按场景分步操作（"如何实现 X"） |
| API Reference | 集成者 | 每个公开接口的签名、参数、返回值、错误码 |
| Changelog / Migration | 维护者 | 版本变更、breaking changes、升级路径 |
| FAQ / Troubleshooting | 所有人 | 常见报错及解决方案 |

## 5. 示例驱动

- 每个概念至少一个最简示例，再逐步叠加复杂度
- 示例是完整的（可复制粘贴运行），不是片段
- 包含**期望输出**，让读者自行验证
- 提供常见错误示例和正确写法的对比

## 6. 最小惊讶

- 遵循行业惯例：目录结构、术语、格式与同领域主流项目对齐
- 明确标注"不做什么"和"边界条件"，而不仅是"正常路径"
- 默认值和隐式行为必须显式说明

## 7. 可维护性

- 单一数据源原则（DRY）：避免多处重复描述同一事实，改一处忘了改另一处
- 优先用代码生成 API 文档（如 `rustdoc`、`TSDoc`），而非手写
- 文档纳入 CI：链接检查、拼写检查、示例代码编译验证
- 有明确的文档负责人和更新频率（或触发机制）

## 8. 语气与风格一致

- 全文档统一人称（"你"而非混用"您/你/开发者"）
- 统一格式规范：标题层级、代码块语言标注、警告/提示框样式
- 风格指南写在 `CONTRIBUTING.md` 或专门的文档规范文件中

## 9. 反馈闭环

- 每页提供"本文有帮助吗？"反馈按钮
- 文档仓库开放 Issue，接受读者纠错
- 定期审查高频搜索词和高跳出率页面，针对性改进

---

**总结**：好文档不是一个静态产物，而是一个**持续匹配读者需求的系统**。写的时候问自己三个问题：

1. 读者是谁？
2. 他/她此时想完成什么？
3. 读完之后能直接行动吗？
