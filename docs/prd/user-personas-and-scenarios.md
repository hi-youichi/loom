# Loom 用户、任务与场景定义

> 状态：讨论稿<br>
> 目的：为产品取舍、可用性测试和 PRD 验收提供共同用户模型

## 1. 目标市场假设

Loom 首先服务于愿意在本地代码和工具环境中使用 AI 的开发者。它的价值不在“比聊天更会回答”，而在“能安全地持续做项目内的真实工作”。团队自动化是第二层用户，而非要求个人用户一开始学习工作流 DSL。

## 2. 核心 Persona

| Persona | 背景 | 主要目标 | 最大顾虑 | 优先入口 |
| --- | --- | --- | --- |
| 本地开发者 | 使用 Git、终端和 IDE 维护代码库 | 排障、实现、测试、重构 | Agent 越界改文件、丢上下文 | CLI、ACP |
| 项目维护者 | 维护规范、依赖和发布质量 | 让重复检查可复用、可审阅 | 自动化不可追溯、输出不可验证 | CLI、工作流 |
| 自动化操作者 | 为小团队运行定期/批处理任务 | 启动、监控、恢复多 Agent 工作 | 失败后不知道谁出了问题 | 工作流、Bot |
| 平台集成者 | 将 Loom 嵌入 IDE 或内部工具 | 获得稳定协议与生命周期 | 行为随入口不同、兼容性不稳 | ACP、CLI |

## 3. 优先 Jobs to be Done

### J1：在已有项目中完成一项变更

当我在一个代码库中遇到明确问题时，我想让 Agent 先理解目录和约束，再搜索、修改、测试并报告证据，以便我能快速审阅而不是从头手工操作。

成功信号：工作目录明确；修改和测试命令可追溯；未验证时明确说未验证；我可用同一会话继续修正。

### J2：在多轮中延续同一工作

当任务跨越多次对话时，我想恢复此前的上下文、模型和项目设置，以便不用重复提供背景，也不会把旧结论错误带到新项目。

成功信号：会话与工作目录绑定；用户可查看、继续、清空或删除；不同会话不会串写。

### J3：把有效经验变为可控的复用能力

当 Agent 多次需要同一项目规范或流程时，我想将其保存为记忆或技能，并在每次使用时看到依据，以便提高效率而不失去控制。

成功信号：作用域和来源明确；支持编辑删除；自动建议先审阅再生效。

### J4：运行和诊断重复性自动化

当一项任务需要并行或长时间执行时，我想启动工作流、查看摘要、只在必要时展开事件，并能取消或恢复，以便控制成本与风险。

成功信号：实例总有终态；大输出有界；失败可定位；不损坏项目目录。

## 4. 关键用户旅程

### 首次任务（开发者）

```text
安装/配置模型 → 在项目目录运行 Loom → 提交任务
→ 看见目录、模型和权限提示 → 审阅工具活动与最终证据
→ 继续会话或结束
```

失败点：密钥配置、目录错误、工具权限、模型选择。每一点都需要给出可执行修复，而不是泛化错误。

### 连续工作（开发者）

```text
选择已有会话 → 恢复项目上下文 → 追加任务
→ 查看加载的记忆/技能 → 完成并选择是否沉淀经验
```

失败点：会话找不到、上下文过期、记忆冲突。用户必须可以回退或不加载。

### 工作流诊断（操作者）

```text
选择工作流 → 后台启动实例 → 查看状态摘要
→ 失败时按 Agent/事件筛选 → 取消、修复或恢复
```

失败点：永久 running、大日志、并发写入、恢复含义不清。产品应优先处理这些问题。

## 5. 非服务对象与边界

- 不把 Loom定位为无需技术判断的全自动软件开发服务。
- 不承诺替代团队的代码审查、安全流程或 CI。
- 不为无本地工作目录、只想通用闲聊的用户优化首屏体验。
- 不在未解决权限、审计与数据边界前，承诺企业级共享自动化。

## 6. 研究问题

| 假设 | 验证方法 | 通过信号 |
| --- | --- | --- |
| 连续上下文是留存关键 | 访谈 + 7 日项目复用观察 | 用户主动继续会话而非新建。 |
| 可解释性比更多模式更重要 | 可用性测试 A/B 任务 | 用户能说清 Agent 做了什么、为何这么做。 |
| 工作流摘要降低诊断成本 | 故障演练 | 多数维护者无需读完整事件即可归因。 |
| 记忆需人工控制 | 访谈 + 删除/审阅任务 | 用户愿意保存并能放心撤销。 |
