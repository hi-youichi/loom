# Loom v0.4 核心 Agent PRD

> 状态：讨论稿<br>
> 产品负责人：待定<br>
> 关联文档：[产品定位与体验原则](loom-product-positioning.md)<br>
> 范围：CLI 主入口与 ACP 的核心一致性；不包含 Telegram Bot 和工作流 DSL 的专项需求

## 1. 背景与目标

Loom 已经提供 Agent、工具、会话、记忆、技能、MCP、模型选择和 ACP 集成，但这些能力更像一组命令，而非一条清晰的持续工作路径。v0.4 的目标不是增加新的推理模式或工具数量，而是让开发者可靠地完成以下闭环：

```text
选择项目 → 发起任务 → 看懂 Agent 的执行 → 继续同一会话
        → 审阅/管理沉淀的上下文 → 在 IDE 中得到一致体验
```

### 目标

1. 新用户可以在一个项目目录中完成一次受控的工具型 Agent 任务。
2. 用户能够明确创建、继续、查看和取消会话，不会丢失工作上下文。
3. 用户能够查看并管理影响 Agent 行为的记忆与技能。
4. CLI 与 ACP 对工作目录、会话、模型和取消的语义保持一致。

### 非目标

- 改变或比较 ReAct、DUP、ToT、GoT 的底层算法。
- 在 v0.4 建成完整的团队协作、云同步或计费体系。
- 让记忆/技能完全自动化生成且无需人工审阅。
- 为所有工具引入交互式图形界面。

## 2. 用户与待完成任务

### 用户 A：独立开发者小林

小林在仓库根目录运行 Loom，要求 Agent 定位一个失败测试、修改代码并运行验证。她需要知道 Agent 实际操作了哪个目录、调用了什么工具、任务是否还在执行，以及下一轮如何继续讨论同一问题。

### 用户 B：IDE 用户小周

小周从支持 ACP 的 IDE 发起同一类任务。他希望模型、工作目录、会话上下文、取消结果与 CLI 一致；关闭再打开 IDE 后，仍可加载或继续会话。

### 用户 C：习惯沉淀者小陈

小陈希望 Loom 记住项目测试命令和代码规范，但不希望隐式注入过期或错误的“记忆”。他需要能看到某条记忆/技能何时被使用，并能编辑或移除它。

## 3. 范围与优先级

| 优先级 | 需求域 | v0.4 交付结果 |
| --- | --- | --- |
| P0 | 任务启动与可见性 | 明确显示工作目录、模型、会话标识与执行状态。 |
| P0 | 会话连续性 | CLI 可创建/继续/查看会话；ACP 会话稳定映射到 Loom thread。 |
| P0 | 取消与失败 | 用户可取消运行；终止状态、错误和安全提示可理解。 |
| P1 | 记忆与技能透明度 | 用户可查看、编辑、删除，并了解本次是否加载/使用。 |
| P1 | CLI/ACP 一致性 | 关键配置和行为有共享语义与契约测试。 |
| P2 | 引导与可发现性 | 根 README 与 `--help` 引导用户走完首个任务。 |

## 4. 用户流程与需求

### 4.1 发起任务

用户在项目目录执行 `loom -m "…"` 或通过 ACP 提交提示。用户可以指定工作目录、模型/提供商/能力层级、Agent profile 和会话标识。

**需求**

- R-01：在任务开始前或首个状态事件中，展示有效工作目录、执行模式、模型/提供商和会话 ID；JSON/ACP 使用机器可读字段提供相同信息。
- R-02：未传工作目录时，清楚说明默认目录；传入不存在或无权访问的目录时，在调用模型前失败。
- R-03：模型、提供商与能力层级冲突时，给出可行动的错误说明，不能静默选择意外模型。
- R-04：文本、图片输入和 MCP 配置失败须分别说明原因与修复动作，不泄露 API key 或完整敏感配置。

**验收标准**

- 使用 `--working-folder` 的运行中，用户可从首屏或 JSON 元数据确认有效路径。
- 无效目录、无效 tier、模型/provider 冲突均在工具调用和 LLM 请求之前失败。
- 普通文本模式不因状态输出污染 `--json` 或 ACP 的协议输出。

### 4.2 运行中观察与取消

Agent 运行可能很久，用户需要看见阶段、工具调用、结果与失败，而不是只能等待最终回复。

**需求**

- R-05：默认人类输出显示精简进度：开始、关键工具调用/阶段、完成或失败；详细内容按 verbose/JSON 获取。
- R-06：每个运行具有可取消的运行句柄。CLI 首次 Ctrl+C 请求优雅取消；重复 Ctrl+C 才能强制退出。
- R-07：取消、超时、工具错误、模型错误和内部错误在最终状态中可区分；用户可得到下一步建议（重试、检查配置、查看日志等）。
- R-08：日志文件是可选的；开启日志时，输出路径和轮转策略可预测，且不能默认记录密钥。

**验收标准**

- 在一次包含延迟工具调用的测试任务中，第一次取消会结束运行且输出 `cancelled` 语义，而不是成功回复或无响应退出。
- CLI JSON 和 ACP 都可接收开始、进度、工具/阶段、终止四类状态，终止事件恰好一次。
- 工具失败不被错误表述为模型已经完成任务。

### 4.3 会话连续性

会话是持续工作的基础对象。CLI 的 `session_id` 与 ACP 的 `session_id` 都应映射到稳定的 Loom thread，保存上下文及会话级配置。

**需求**

- R-09：用户可用显式 `session_id` 继续对话；交互模式自动复用该轮会话 ID。
- R-10：用户可列出、查看和删除 CLI 会话。列表至少包含 ID、标题/摘要（若有）、最近更新时间和工作目录。
- R-11：ACP 的新建、加载、fork、提示和取消操作使用稳定 session/thread 映射；会话级模型、模式、effort 配置可恢复。
- R-12：`/reset` 或等价操作清除对话上下文时，明确说明影响范围；它不得无意删除用户记忆、技能或项目文件。

**验收标准**

- 两次 CLI 调用使用同一 `session_id` 时，第二次能访问第一轮的对话上下文。
- CLI 删除会话后，后续继续请求得到明确的“会话不存在”结果；不会误创建一个看似相同的空会话。
- ACP 重启后加载同一 session，工作目录及已持久化的会话配置保持一致。
- fork 后源会话与新会话的后续对话不会互相写入。

### 4.4 记忆与技能的可控沉淀

记忆和技能能提高连续任务的质量，但也是隐式行为的来源。因此 v0.4 优先解决透明度和可控性。

**需求**

- R-13：用户可通过 CLI 列出、查看、编辑和删除记忆与技能；每项展示名称、来源/作用域、最后更新时间。
- R-14：任务开始或 verbose 视图能说明加载了哪些记忆和技能；若无加载，也应可区分“无匹配”与“功能未启用”。
- R-15：技能使用跟踪至少记录使用时间、会话/项目关联和结果状态；失败的跟踪不能阻断 Agent 主任务。
- R-16：会话复盘产生的记忆/技能更新默认是可审阅的建议，包含来源会话和建议内容；用户确认前不得覆盖现有项。
- R-17：删除记忆/技能前说明影响范围；删除后新运行不再加载该项。

**验收标准**

- 用户创建一条项目级记忆后，可以在列表中找到，且在同项目后续运行的详细状态中可见其加载原因。
- 用户删除该记忆后，在相同条件下再次运行不再加载它。
- 一次 skill usage 存储写入失败不导致 Agent 运行失败，并留下可诊断日志。

### 4.5 CLI 与 ACP 一致性

CLI 是可观测、可脚本化的基准入口；ACP 是 IDE 原生体验的入口。二者不必使用同一 UI，但不能出现核心语义差异。

**共享契约**

| 对象 | 一致性要求 |
| --- | --- |
| 工作目录 | 解析规则、默认值和错误语义一致。 |
| 会话 | 一个 ACP session 对应一个 Loom thread；生命周期和清空语义明确。 |
| 模型配置 | provider、model、tier/effort 的优先级一致，持久化范围明确。 |
| 工具 | 受支持工具及权限/失败语义一致；入口只改变呈现方式。 |
| 取消 | 均能请求取消、等待终止并呈现取消状态。 |
| 输出 | 人类摘要与机器事件可映射；协议通道不得混入日志或调试文本。 |

**验收标准**

- 对同一 fixtures 项目、相同模型与提示，CLI 和 ACP 产生等价的工作目录、会话关联和终止类别。
- ACP server 的 stdout 只输出协议数据；配置报告和日志不污染协议。
- 共享契约有自动化集成测试，而不是只依赖人工对比。

## 5. 信息与状态模型

每次运行对外至少包含以下对象。内部 Rust crate 如何拆分不应影响该模型。

```text
Project / working directory
  └─ Session (thread, 可选)
       └─ Run
            ├─ Input + effective configuration
            ├─ Progress events / tool activity
            ├─ Final outcome: completed | failed | cancelled
            └─ References: logs, files, memories, skills
```

运行结果中的 `completed` 只表示运行正常终止，不表示 Agent 的业务结论必然正确。需要验证的任务，最终摘要必须保留“已验证/未验证”及验证证据。

## 6. 数据与安全约束

- 默认在用户指定项目和本地 Loom 数据目录中保存会话、配置和运行产物；新增远程同步不属于本 PRD。
- 密钥仅从环境变量或明确配置读取；界面、日志、错误与事件中必须脱敏。
- 文件、Shell、浏览器和 MCP 工具的访问范围必须可解释。若默认允许项目目录外路径，文档和运行提示必须明确告知风险。
- `--worktree` 是高风险修改任务的推荐隔离手段；它的创建、保留和清理结果必须对用户可见。
- 删除会话、记忆或技能是破坏性操作，命令帮助和输出必须清楚标识目标与后果。

## 7. 发布门槛

v0.4 可以发布核心 Agent 体验，需同时满足：

1. P0 验收标准均有自动化覆盖或可重复的端到端测试脚本。
2. `loom --help`、根 README 与 CLI 实际命令一致；未实现的 `evolve` 不作为推荐流程出现。
3. CLI/ACP 会话和取消的一致性测试通过。
4. 记忆/技能的创建、查看、删除和加载可解释路径至少覆盖一个真实项目 fixture。
5. 已记录已知限制：Telegram Bot、浏览器扩展、任务模式、工作流实例模型的成熟度及支持边界。

## 8. 开放决策

1. v0.4 的默认 Agent mode 是 ReAct，还是依据任务自动选择？自动选择需先提供可解释理由。
2. 是否将项目外文件访问改为显式授权，或至少在首次使用时发出确认？
3. 记忆和技能的默认作用域应是用户级、项目级，还是会话级？冲突时谁优先？
4. 自动复盘的触发时机、模型成本上限和用户确认机制是什么？
5. ACP 客户端差异如何分级支持，哪些扩展能力需要降级策略？
