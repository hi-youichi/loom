# Loom 产品定位与体验原则

> 状态：讨论稿<br>
> 适用版本：v0.4 开发中<br>
> 目标读者：产品、研发、设计，以及需要理解 Loom 产品边界的贡献者

## 1. 一句话定位

Loom 是一个**本地优先、可跨入口持续工作的 AI Agent 运行环境**：它让开发者和技术团队能够在 CLI、IDE 与消息 Bot 中运行 Agent，并让 Agent 调用工具、延续会话、沉淀记忆与技能，以及执行可观察、可恢复的工作流。

Loom 不是只回答问题的聊天机器人，也不只是供其他项目调用的 Agent SDK。它的长期目标是让一次次零散的 Agent 协作，逐步变成可复用的个人或团队工作能力。

## 2. 要解决的问题

现有 AI 编程和自动化工具通常有三个断点：

1. **入口断裂**：终端、IDE、聊天工具各自保存上下文；用户换一个入口，就要重新说明任务和约束。
2. **能力不沉淀**：一次成功的排障、代码规范或项目习惯留在对话里，下一次仍要重复提示。
3. **复杂任务不可控**：多步骤或多 Agent 任务缺少明确的状态、事件、取消、恢复和结果检查机制。

Loom 以本地工作目录、`.loom/` 配置/产物和可替换的模型、工具、持久化组件为中心，解决“Agent 如何持续完成真实工作”而非只解决“如何生成一次回答”。

## 3. 目标用户与优先场景

### 核心用户：使用本地代码库的开发者

他们需要 Agent 读写项目文件、运行命令、使用浏览器或 MCP 工具，并希望在长任务或多轮任务中保留上下文。

典型场景：

- 在 CLI 中分析、修改、测试本地代码；必要时在隔离 Git worktree 中运行。
- 在 IDE 中通过 ACP 调用同一类 Agent 能力，而非维护另一套行为模型。
- 将项目约定、个人偏好和成功做法沉淀为记忆或技能，供后续会话使用。

### 次级用户：构建内部自动化的技术团队

他们需要将重复的研究、审核、拆解或批处理工作写成可执行工作流，并能够定位执行状态和失败原因。

典型场景：

- 以 Lua 描述多 Agent 任务编排，执行并检查工作流实例。
- 在 Telegram 等消息入口中部署面向特定团队或用途的 Agent Bot。
- 按模型供应商、模型能力层级和成本/可靠性要求配置运行策略。

### 当前非目标

- 面向非技术大众的通用聊天产品。
- 托管式、多租户 SaaS 协作平台。
- 替代 Git、项目管理或企业知识库系统。
- 承诺所有 Agent 执行结果正确；Loom 应提供验证、审阅和可追溯能力，而不是掩盖不确定性。

## 4. 产品价值主张

| 用户需求 | Loom 提供的价值 |
| --- | --- |
| 让 Agent 真正操作工作环境 | 统一的工具系统，可接入文件、Shell、Web、MCP 与扩展工具。 |
| 在多次任务间不从零开始 | 会话、checkpoint、记忆和技能体系，支持持续上下文。 |
| 适配不同模型与部署偏好 | 提供商配置、模型选择和 light / standard / strong 能力层级。 |
| 把复杂任务做得可控 | 图式 Agent 运行模式与工作流实例、事件、取消、恢复、结构化输出能力。 |
| 在习惯的入口使用 | CLI 是基础入口；ACP 用于 IDE；Telegram Bot 用于消息场景。 |

## 5. 核心体验原则

### 5.1 工作目录是上下文边界

每次运行应明确其工作目录。项目特有的工具、MCP、Agent 配置、技能和运行产物优先归属该目录；用户应能理解 Agent 可以访问什么、在哪里写入结果。

### 5.2 先给结论，再按需展开证据

Agent、工具和工作流的默认输出应短而可操作：显示结果、状态和下一步；日志、事件流、原始产物和大文件只在用户显式请求时展开。工作流的“实例摘要 → 事件分页 → 源码”模型是这一原则的基准。

### 5.3 每个长任务都必须可中断、可解释、可续接

用户应随时知道任务是否仍在运行、已经做了什么、为何失败；取消不应留下不可理解的半成品。对于可恢复工作流，应保留足够的状态和事件以继续或诊断。

### 5.4 能力沉淀必须由用户掌控

记忆和技能会影响未来行为，必须可查看、编辑、删除和追溯来源。自动从会话中提出的技能或记忆更新，应以建议/审阅为主，不应悄然改变用户环境。

### 5.5 多入口应共享能力模型，而不是复制产品

CLI、ACP 和 Bot 可以有不同交互方式，但应复用同一个 Agent、工具、模型和持久化基础。入口差异不应导致项目规则、权限语义或任务结果不一致。

## 6. 当前产品能力地图

下表描述仓库中已实现或正在实现的能力，不代表全部能力已达到稳定发布标准。

| 能力域 | 当前状态 | 产品说明 |
| --- | --- | --- |
| CLI Agent | 已具备 | 提供 ReAct、DUP、ToT、GoT 运行模式，支持单次运行与交互式会话。 |
| 模型与提供商 | 已具备 | 通过配置选择提供商、模型和能力层级；可在单次运行中覆盖。 |
| 工具与 MCP | 已具备 | 支持工具查看/管理、MCP 服务管理，以及面向 Agent 的可插拔工具来源。 |
| 会话与持久化 | 已具备 | 支持会话标识、checkpoint 与 SQLite 相关存储组件。 |
| 记忆与技能 | 已具备，体验待统一 | 包含记忆、技能管理、技能使用跟踪和会话复盘入口。 |
| ACP IDE 集成 | 已具备 | 作为 ACP server 运行，让兼容客户端接入 Loom Agent。 |
| Telegram 多 Bot | 已具备 | 单进程多 Bot、流式消息和命令体系已有独立文档。 |
| 浏览器自动化扩展 | 实验性 | 通过 MCP 与 Chromium 浏览器扩展互通。 |
| 多 Agent 工作流 | 可用且在重构 | Lua 工作流、并行执行、事件、取消/恢复与结构化输出存在；实例模型和渐进式查看体验仍在演进。 |
| 任务/公司模式 | 实验性 | 已有 task 相关命令与 crate，需在产品上明确人机协作模型和稳定性边界。 |
| Evolve | 未实现 | CLI 中保留入口，但当前会明确提示未实现，不应出现在对外价值承诺中。 |

## 7. 理想用户旅程

```text
选择项目与入口
  → 运行 Agent，调用本地/远程工具完成任务
  → 保存可继续的会话与运行状态
  → 审阅结果，将可复用经验提炼为记忆或技能
  → 将重复工作升级为工作流或专用 Agent
  → 在 CLI、IDE、Bot 等入口持续复用
```

产品设计的关键不是要求所有用户走完整旅程：CLI 编程助手可以只使用前两步；团队自动化用户可以直接从工作流开始。但这些能力应使用一致的配置、身份、权限与可观察性模型。

## 8. 产品信息架构建议

对用户呈现时，建议围绕工作对象组织，而非按 Rust crate 或底层算法组织：

1. **开始工作**：运行 Agent、选择模型、设定工作目录、管理会话。
2. **扩展能力**：工具、MCP、浏览器、Agent 配置与技能。
3. **积累上下文**：记忆、技能使用、会话复盘。
4. **自动化工作**：工作流、实例、任务、取消与恢复。
5. **接入入口**：CLI、IDE/ACP、Telegram Bot。
6. **配置与安全**：提供商密钥、文件访问范围、日志、数据存储和故障排查。

根目录 README 应服务“5 分钟理解和跑通”；各入口 README 服务安装与操作；设计文档保留实现决策。不要让用户先学习图执行、crate 边界或内部协议才能理解产品价值。

## 9. 成功指标（待产品负责人确认）

首个版本建议不以模型调用量为目标，而用下列行为衡量：

| 指标 | 定义 | 目的 |
| --- | --- | --- |
| 首次任务成功率 | 新用户完成一次带工具的有效任务的比例 | 验证上手体验。 |
| 连续任务率 | 同一项目在 7 天内被再次使用的比例 | 验证持续工作价值。 |
| 沉淀复用率 | 被后续运行实际加载或调用的记忆/技能占比 | 验证“越用越懂”的承诺。 |
| 工作流可诊断率 | 失败实例可从摘要和有限事件中定位原因的比例 | 验证自动化可控性。 |
| 入口一致性 | 同一项目在 CLI/ACP/Bot 的核心任务成功率差异 | 防止多入口能力割裂。 |

在本地优先前提下，指标采集必须为可选、可解释，并避免默认上传用户代码或提示内容。

## 10. 近期产品优先级建议

### P0：统一核心叙事与可发现性

- 重写根 README：以“持续工作的 AI Agent 环境”为主线，展示一个从 CLI 到会话/技能/工作流的真实路径。
- 明确标记稳定、实验性和未实现能力；清理或隐藏无法使用的入口。
- 定义 `.loom/` 的用户可见目录契约和数据生命周期。

### P1：让持续性体验闭环

- 统一会话、记忆、技能和复盘的用户路径与命名。
- 提供“本次运行加载了什么记忆/技能、为何加载”的可解释视图。
- 为 CLI 与 ACP 建立一致的会话恢复、取消和状态展示体验。

### P2：把工作流做成可信自动化

- 完成以 instance 为中心的工作流查看模型：列表、摘要、分页事件、执行源码。
- 明确恢复语义、失败类型、结构化报告和人工审阅点。
- 先打磨少量高价值工作流模板，再扩大 DSL 能力面。

## 11. 需要决策的问题

本文件确立了“持续工作环境”作为暂定主线，但以下问题需要产品决策：

1. **主入口**：未来 6–12 个月优先 CLI、IDE/ACP，还是团队 Bot？资源不能平均分配。
2. **核心付费/交付对象**：个人开发者、开发团队，还是为内部平台集成 Loom 的工程团队？
3. **本地优先的边界**：哪些数据可跨设备/团队同步，哪些必须永不离开本机？
4. **自动化的授权模型**：文件访问、Shell、浏览器与工作流应采用何种默认权限和审阅机制？
5. **稳定性承诺**：哪些模块进入稳定 API，哪些继续保留为 experimental？

这些结论应在后续 PRD 中转为具体范围、验收标准和路线图，而不是由实现细节隐式决定。
