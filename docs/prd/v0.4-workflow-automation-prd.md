# Loom v0.4 工作流自动化 PRD

> 状态：讨论稿<br>
> 关联：[产品定位与体验原则](loom-product-positioning.md)、[核心 Agent PRD](v0.4-core-agent-prd.md)<br>
> 范围：`tool-workflow` 的面向用户契约与工作流实例体验；不规定 Lua 运行时的内部实现

## 1. 背景与问题

Loom 已能以 Lua 编排多个 Agent，支持并行执行、事件、checkpoint、取消和结构化输出。但当前体验有两个风险：

1. 执行结果容易一次性返回完整 checkpoint、事件和源码；长工作流会产生大量内容，用户和调用 Agent 都难以判断下一步。
2. “运行（run）”既指命令、进程、原始运行目录，也指用户想要查看的工作成果；恢复、诊断与历史浏览缺少稳定的产品对象。

v0.4 将“工作流实例（instance）”定义为唯一面向用户的执行对象，并以**摘要优先、按需展开、可恢复、可诊断**为体验原则。

## 2. 目标与非目标

### 目标

- 用户能启动一个工作流，在不读取原始文件的情况下理解它是否完成、失败或取消。
- 用户能从实例列表定位历史执行，并用有限事件定位失败原因。
- 每个实例都有可追溯的执行输入、源码快照、状态、Agent 概况和报告。
- 长运行支持取消；中断或崩溃后的工作可从明确的实例恢复。
- 大型输出不会淹没用户、聊天上下文或工具调用结果。

### 非目标

- 设计通用可视化 DAG 编辑器。
- 对任意 Lua 脚本做静态副作用分析或完全预演。
- 在 v0.4 支持分布式调度、跨机器接管或团队级队列。
- 将“已完成”解释为业务结果已经由人或外部系统确认正确。

## 3. 用户与关键场景

| 用户 | 场景 | 成功标准 |
| --- | --- | --- |
| 开发者 | 把重复的代码审查/调研任务保存为工作流并运行 | 只看摘要就知道结果、成本和待处理项。 |
| 任务操作者 | 工作流失败后找出异常 Agent 与对应阶段 | 通过摘要和少量筛选事件定位根因，无需下载全部日志。 |
| 自动化 Agent | 运行后台工作流并轮询结果 | 获得稳定、分页、机器可读的接口，不把大文件塞进上下文。 |
| 维护者 | 崩溃/取消后恢复长任务 | 明确能否恢复、从何处恢复，以及哪些步骤会重跑。 |

## 4. 概念与信息模型

### 4.1 名词

- **工作流（workflow）**：用户编写或内联传入的 Lua 编排定义。
- **实例（instance）**：一次工作流执行及其全部可追溯产物。对外不再以 `run` 作为主名词。
- **阶段（phase）**：工作流内的逻辑执行区段。
- **Agent 执行项**：实例中一个具体 Agent 的启动、输出和终止记录。
- **报告（report）**：工作流产生的最终结构化结果；它可能内联，也可能以受控引用方式保存。

### 4.2 生命周期

```text
created → running → completed
                  ↘ failed
                  ↘ cancelled

failed / cancelled / interrupted → resumable（仅在运行时支持且检查点有效时）
```

`completed` 只说明运行时正常终止；报告中应保留验证状态和证据，不能把技术完成混同为任务正确。

### 4.3 存储边界

新实例的用户可见产物属于 `<working_folder>/.loom/`：

```text
.loom/
  workflows/                 # 用户维护的 .lua 定义
  instances/<instance-dir>/
    instance.json            # 稳定、精简的实例摘要
    checkpoint.json          # 恢复用原始状态
    events.jsonl             # 仅供分页诊断的事件流
    workflow.lua             # 本次执行的源码快照
    report.json              # 大型结构化报告（可选）
    agent-outputs/           # 大型 Agent 输出（可选）
```

旧 `.luft/runs/` 记录在兼容期内可读取，列表必须标注 `source: legacy`。新执行不得继续创建 Loom 所有的 `.luft/` 路径。

## 5. 功能需求

### 5.1 工作流发现与启动

- W-01：用户可列出 `.loom/workflows/` 下的可执行 Lua 工作流，结果包含名称、大小和简短首行/描述，不返回完整源码。
- W-02：用户可用工作流名称/路径或内联脚本启动实例；两种输入互斥。
- W-03：启动参数支持 JSON `args` 和 `concurrency`（1–64，默认 4）。参数校验失败必须在 Agent 消耗 token 前返回。
- W-04：启动为后台操作，立即返回 `instance_dir` 和 `status: running`；调用者可轮询，不应阻塞等待全部 Agent 完成。
- W-05：同一工作目录默认只允许一个可写工作流实例。冲突时返回当前持有者的可诊断信息，不得悄悄并发写入。

**验收**：一个有效工作流在启动后 1 秒内返回实例 ID；并发启动第二个写实例时，得到明确冲突而非数据竞争。

### 5.2 实例状态与摘要

- W-06：`workflow_status(instance_dir)` 在运行中只返回轻量状态；终止后返回实例摘要。
- W-07：终态摘要至少包含：实例 ID、状态、工作流标识、开始/完成时间、总 token、Agent 数、每个 Agent 的状态/耗时/token/有界输出预览、阶段跨度、事件统计和报告预览。
- W-08：摘要必须有 schema version，且不直接嵌入完整 `events.jsonl`、完整源码、大型 Agent 输出或大型报告。
- W-09：每个已启动 Agent 最终必须对应一个 `agent_done`；每个实例最终必须有且仅有一个终态 `run_done`。异常流关闭时，运行时应合成带失败原因的终态事件。
- W-10：状态至少区分 `completed`、`failed`、`cancelled`；错误需同时给出人类可读摘要和稳定的 `failure_kind`（若运行时可提供）。

**验收**：含 1000 条事件的实例状态响应保持在约定的有界大小内；事件通道提前关闭时，用户仍能拿到一个失败终态，而不是永久 `running`。

### 5.3 历史列表与渐进式诊断

- W-11：用户可分页列出实例，默认 20 条、最大 100 条，支持 `completed`、`failed`、`cancelled` 状态过滤。
- W-12：列表项仅含实例 ID、状态、工作流名称、时间、token 总量和 Agent 数；不含原始路径、大输出或全部报告。
- W-13：用户可按 `offset`、事件类型和 Agent ID 分页获取事件；默认 50 条、最大 500 条。无效/空事件行应被跳过并计数，不致使整个查询失败。
- W-14：用户可获取本实例执行时的源码快照，响应受大小上限限制且返回 `truncated`；源码快照不可被当前文件覆盖。
- W-15：所有诊断流遵循固定顺序：**实例列表 → 实例摘要 → 过滤事件 → 必要时看源码**。工具描述、技能文档和示例都必须教会这一顺序。

**验收**：失败实例可通过“列表 + 摘要 + 只筛选 `agent_done`/`run_done` 事件”完成根因定位；不会自动读取完整事件文件。

### 5.4 大输出与报告

- W-16：结构化报告在小于 800 UTF-8 bytes 时可内联；超出时写入 `report.json` 并仅返回类型、大小和有界预览。
- W-17：单个 Agent 输出超过 2 KB 时写入 `agent-outputs/`，摘要仅保留前 400 字符预览、大小和受控引用。
- W-18：引用必须相对实例目录，不能暴露绝对路径，也不能让调用者借此读取实例外任意文件。
- W-19：报告和输出的序列化/落盘失败必须将实例标记为可诊断失败，不能错误报告为 `completed`。

**验收**：10 MB 报告与 100 KB Agent 输出不会使状态工具响应超过约定大小；用户仍能从摘要判断是否需要进一步处理。

### 5.5 取消与恢复

- W-20：用户可取消当前进程拥有的运行中实例；立即返回 `cancelling`，并通过状态轮询观察终态。
- W-21：不存在、已终态或由其他进程拥有的实例取消请求返回 `not_found_or_terminal`，不得误取消其他工作。
- W-22：用户可从崩溃或中断实例发起恢复；恢复创建新实例，并记录 `resumed_from`，保留源实例不可变。
- W-23：恢复前必须校验 checkpoint 可用性、脚本/输入兼容性和允许的恢复模式；不满足时给出“为何不能恢复、建议重新运行还是修复”的说明。
- W-24：取消后的恢复能力不得假定存在。若当前运行时不支持从取消恢复，产品需明确提示“重新启动”而不是制造虚假的恢复入口。

**验收**：取消后实例最终为 `cancelled`；从可恢复的中断实例恢复后，新实例正确连接源实例且不改写原事件和检查点。

## 6. 接口与兼容策略

v0.4 对外工具采用以下逻辑面，而不要求一次性兼容所有旧命名：

| 逻辑能力 | 推荐接口 | 旧接口处理 |
| --- | --- | --- |
| 启动 | `workflow_start` | `run` 在一个小版本内给出迁移提示。 |
| 状态摘要 | `workflow_status` | 不再返回完整 checkpoint + 全事件 + 全源码。 |
| 取消 | `workflow_cancel` | 新增稳定语义。 |
| 实例列表 | `workflow_list` | `list-runs` 迁移到分页实例列表。 |
| 事件 | `workflow_events` | 从状态接口拆分。 |
| 源码 | `workflow_source` | 从状态接口拆分。 |
| 工作流文件 | `workflow_files` | 保持轻量列举。 |

内部实现可以继续使用 `RunHandle`、`run_id` 与现有 Luft 组件；序列化边界和用户文档必须统一使用 instance 术语。

## 7. 安全与可靠性约束

- 工作流默认获得工作目录锁；锁需依赖跨进程 OS 级独占机制，诊断元数据不能代替真正的锁。
- 并发参数控制 Agent 并行度，不等价于允许多个工作流同时写同一目录。
- 取消、任务 panic、事件通道关闭、Agent 超时和模型失败都必须终结实例，释放锁并留下诊断。
- 任意 Lua 的写入集合在 v0.4 不做自动推断；只有显式声明只读且被产品接受的例外才能绕开默认锁。
- 不记录或展示密钥；实例产物中的 prompt、输出和源码属于用户工作数据，保留与清理策略必须可文档化。

## 8. 指标与发布门槛

| 指标 | 定义 |
| --- | --- |
| 实例终态完整率 | 已启动实例拥有恰好一个终态事件的比例。 |
| 可诊断率 | 失败实例仅凭摘要和不超过两页筛选事件即可归类根因的比例。 |
| 大输出受控率 | 超过阈值的报告/输出不内联到状态响应的比例。 |
| 恢复成功率 | 符合恢复条件的中断实例成功创建后继实例的比例。 |

发布前必须满足：

1. 启动、轮询、取消、失败、事件通道异常、输出截断和恢复各有端到端测试。
2. 工作目录锁通过同进程和跨进程冲突测试；进程崩溃后锁可安全释放或给出明确恢复操作。
3. 新 `.loom/instances/` 结构、legacy 读取和迁移时限有用户文档。
4. `workflow` skill 的主文档以决策树和诊断流程为主，Lua DSL 细节移至参考文件。

## 9. 开放决策

1. 工作流的 API 命名最终采用 `workflow_*` 还是通用 `instance-*` action？需要与全局工具命名体系统一。
2. `report.json`/Agent 输出是否允许由工具直接读取，还是始终通过有界预览提供？需要在可用性与上下文安全之间选择。
3. 恢复模式（resume、retry-agent、rerun-phase）何时能由底层运行时稳定支持？在此之前如何显式降级？
4. 工作目录锁的“只读并发”例外是否在 v0.4 开放，还是完全延后以保证正确性？
5. 实例保留时长、清理命令和磁盘配额的默认策略是什么？
